[322] 03  —  Anti-Loop Architecture
[323] The previous app was destroyed by cascading data fetches — useEffects that triggered state updates that triggered more useEffects. This section defines the patterns to prevent that from ever happening again.
[325] NEVER put a state setter inside a useEffect whose dependency array contains the same state. NEVER fetch inside a component that re-renders every time its parent re-renders without memo protection.
[327] Rule 1 — Single Data Layer
[328] All Supabase calls live in one place: src/services/. Components never import supabase directly.
[329] Folder structure — services layer
[330] src/
[331]   services/
[332]     supabase.ts          ← client init only
[333]     authService.ts       ← login, register, session
[334]     profileService.ts    ← getProfile, updateProfile
[335]     challengeService.ts  ← getChallenges, createChallenge
[336]     matchService.ts      ← submitMatch, getHistory
[337]     feedService.ts       ← getFeed (one-shot, no realtime)
[338]     messageService.ts    ← getMessages, sendMessage
[339]     rivalryService.ts    ← getRivalries, updateRivalry
[341] Rule 2 — useEffect Dependency Rules
[342] Every useEffect that fetches data must follow this exact pattern:
[343] // ✅ SAFE — fetches once when ID changes, no state in deps
[344] useEffect(() => {
[345]   if (!userId) return;
[346]   let cancelled = false;
[347]   fetchProfile(userId).then(data => {
[348]     if (!cancelled) setProfile(data);
[349]   });
[350]   return () => { cancelled = true; };
[351] }, [userId]);  // ← primitive value, not an object
[353] // ❌ DANGEROUS — object in deps causes infinite loop
[354] useEffect(() => {
[355]   fetchSomething(user);  // user object changes ref every render
[356] }, [user]);
[358] // ✅ FIX — extract the primitive
[359] useEffect(() => {
[360]   fetchSomething(user.id);
[361] }, [user.id]);
[363] Rule 3 — No Polling in Components
[364] The old messaging used setInterval inside components — this caused multiple intervals to stack. Use a single polling hook instead:
[365] // src/hooks/usePolling.ts
[366] export function usePolling(fn: () => void, intervalMs: number) {
[367]   useEffect(() => {
[368]     fn(); // initial call
[369]     const id = setInterval(fn, intervalMs);
[370]     return () => clearInterval(id); // always clean up
[371]   }, []); // ← empty deps: runs once, cleans up on unmount
[372] }
[374] // Usage in Messaging.tsx
[375] const loadMessages = useCallback(() => {
[376]   fetchMessages(channel).then(setMessages);
[377] }, [channel]);
[379] usePolling(loadMessages, 5000);
[381] Rule 4 — Auth State in Context Only
[382] Auth state must live in a single React Context at the root. No component fetches session state directly.
[383] // src/context/AuthContext.tsx
[384] const AuthContext = createContext<AuthContextType>(null);
[386] export function AuthProvider({ children }) {
[387]   const [user, setUser] = useState(null);
[388]   const [profile, setProfile] = useState(null);
[389]   const [loading, setLoading] = useState(true);
[391]   useEffect(() => {
[392]     // Get initial session
[393]     supabase.auth.getSession().then(({ data }) => {
[394]       setUser(data.session?.user ?? null);
[395]       setLoading(false);
[396]     });
[398]     // Listen for changes — fires once on mount
[399]     const { data: { subscription } } = supabase.auth.onAuthStateChange(
[400]       (event, session) => setUser(session?.user ?? null)
[401]     );
[402]     return () => subscription.unsubscribe();
[403]   }, []); // ← empty deps, runs once
[405]   // Fetch profile separately, triggered by user.id
[406]   useEffect(() => {
[407]     if (!user?.id) { setProfile(null); return; }
[408]     fetchProfile(user.id).then(setProfile);
[409]   }, [user?.id]); // ← primitive, safe
[411]   return <AuthContext.Provider value={{ user, profile, loading }}>
[412]     {children}
[413]   </AuthContext.Provider>;
[414] }
[416] Rule 5 — Component Checklist
[417] Before writing any component that fetches data, verify:
[418] deps array contains only primitive values (string, number, boolean) — not objects or arrays
[419] every fetch has a cancelled guard or cleanup function
[420] no setInterval without a matching clearInterval in the cleanup return
[421] no fetch triggered by a state variable that the same fetch also sets
[422] if the component is inside a list (.map()), all fetches use the item's id as the dep, not the item object
[425] 04  —  Build Phases
[426] Seven phases. Each phase ends with a working, testable app. Never start a new phase until the current one is stable. The AI verification feature is deliberately last — it is additive and cannot break anything else.
[431] By the end of Phase 1 you can log in, log out, and see a placeholder dashboard. Nothing else works yet. This phase is entirely infrastructure.
[433] Tasks
[435] Phase 1 complete when: you can register, the profile auto-creates via trigger, you can log in and see the shell, you can log out.
[439] Full profile page for self and other players. Edit avatar/banner URL. Display MMR tier with colour. This phase defines the identity layer the whole app builds on.
[441] Tasks
[443] Phase 2 complete when: own profile is editable and saves to Supabase. Other profiles are viewable. Tier badge renders correctly.
[447] The heart of the app. Players submit match results manually (no screenshot required yet), MMR updates, match history records the entry, and the activity feed gets a write. This phase makes the app actually functional for tracking competitive games.
[449] AI verification is NOT in this phase. Players submit their own score and result (win/loss). Proof screenshot upload is optional in Phase 7. This keeps Phase 3 simple and reliable.
[451] Tasks
[453] Phase 3 complete when: submitting a result updates MMR, writes to history, and writes to the feed. The core competitive loop works end-to-end.
[457] With real data flowing, now build the pages that display it. Community shows all players. Leaderboard ranks them. Activity Feed shows recent events. Dashboard ties it all together.
[459] Tasks
[461] Phase 4 complete when: Community, Leaderboard, and Dashboard are all populated with real data from Supabase.
[465] The most unique feature set. Duels are challenges sent between players. Nemesis status triggers when one player achieves net +3 wins against another. Dog Tags are claimed from those nemesis victories. This phase brings the competitive edge.
[467] Nemesis Logic (important — read before building)
[469] Tasks
[471] Phase 5 complete when: challenges can be sent, accepted, and resolved. Rivalry scores update correctly. Nemesis status triggers at net +3.
[475] Circuits are seasons that contain tournaments. Admin users create circuits and tournaments. Regular players register and view standings. This phase is primarily display + admin tooling.
[477] Tasks
[479] Phase 6 complete when: circuits and tournaments are viewable. Admin can create them. Players can register.
[483] The final phase adds messaging, documentation, and the optional AI screenshot verification. Everything in this phase is additive — it cannot break the existing functionality.
[485] Tasks
[487] Phase 7 complete = app is done. You have a fully functional Digi Leagues rebuild with the new design system and no cascade loops.

PHASE 5  ·  Rivalry System
Daily Duels · Nemesis · Dog Tags · Challenge flow
--- Table 18 ---
Tracking | The rivalries table tracks player_wins, rival_wins, and net_score per pair. Each pair has TWO rows — (A→B) and (B→A).
Nemesis crown | When net_score reaches +3, is_nemesis = true. Player A becomes B's nemesis.
Dog Tag | When is_nemesis becomes true AND dog_tag_claimed = false, a dog tag entry is created on the nemesis player's profile.
Redemption | B wins 2 consecutive duels against A → net_score resets to 0, is_nemesis = false, dog_tag_claimed = false.
3-limit rule | Max 3 challenges per 24h per pair. Track in challenges table — count rows in last 24h.
